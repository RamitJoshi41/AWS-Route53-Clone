# Decision Log

This log tracks architectural and technical decisions made during the development of the AWS Route53 Clone.

| Date | Decision | Options Considered | Chosen | Reason |
| :--- | :--- | :--- | :--- | :--- |
| 2026-10-08 | Next.js Routing | App Router vs. Pages Router | **App Router** | Modern standard, better performance via server components. |
| 2026-10-08 | UI Component Library | Custom CSS vs. Tailwind vs. AWS Cloudscape | **AWS Cloudscape** | Guarantees a pixel-perfect Route53 look with minimal custom CSS. |
| 2026-10-08 | Backend ORM | SQLAlchemy vs. Raw SQLite | **SQLAlchemy** | Industry standard for FastAPI; safer queries and easier relationships. |
| 2026-10-08 | Client State Management | React Query vs. Context API | **React Query** | Excellent for managing server state, caching, and loading/error states. *(Installed in Phase 2; first used for auth state.)* |
| 2026-10-08 | Migration strategy | Alembic vs. `Base.metadata.create_all()` vs. manual SQL | **Alembic** | Versioned, reviewable schema history; schema changes don't require deleting the DB. `env.py` reuses the app engine (one source of truth for the URL), with `render_as_batch=True` because SQLite can't `ALTER` most columns in place. |
| 2026-10-08 | Frontend ↔ backend connectivity | Next.js `rewrites` proxy vs. direct cross-origin calls with CORS | **Proxy + CORS allowlist** | Browser only talks to the Next origin, so the httpOnly session cookie is same-origin (no `SameSite=None`/third-party cookie issues when hosted). FastAPI still has `CORSMiddleware` with an explicit origin list from `CORS_ORIGINS` (never `*`, which browsers reject with credentials). |
| 2026-10-08 | Ports | 3000/8000 vs. 3000/8080 | **3000 / 8000** | Framework defaults; overridable via env. |
| 2026-10-08 | Health endpoint | Liveness only vs. liveness + DB check | **`GET /api/health` with `SELECT 1`** | Proves the full browser → proxy → API → DB chain; returns `503` with `"database":"error"` so monitors and the UI can tell "API down" from "DB down". |
| 2026-10-08 | Python tooling | venv + pip + requirements.txt vs. uv + pyproject.toml | **uv + pyproject.toml + uv.lock** | Fast, reproducible installs from a lockfile; `uv sync` is a single setup command. |
| 2026-10-08 | Sync vs. async route handlers | `async def` vs. `def` | **`def` for any DB-touching route** | SQLAlchemy sessions are synchronous; `async def` would block the event loop. FastAPI runs `def` handlers in a threadpool. |
| 2026-10-08 | Hosted zone primary key | Auto-increment integer vs. Route 53-style string ID | **String ID, e.g. `Z148QEXAMPLE8V`** | Matches the real Route 53 console/API (IDs shown in tables and URLs), increasing fidelity. Implemented in Phase 3. |
| 2026-10-09 | Body hydration warning | `suppressHydrationWarning` on `<body>` vs. ignore | **`suppressHydrationWarning` on `<body>` only** | Browser extensions inject attributes (e.g. `class="vc-init"`) before hydration. Suppression applies to `<body>`'s own attributes only; mismatches inside the app are still reported. |
| 2026-10-09 | Next.js Cache Components | Keep `cacheComponents: true` + `<Suspense>` vs. disable vs. patch Cloudscape | **Disabled** | Cloudscape's `Button` calls `Date.now()` during render (internal analytics ID), which makes `next build` fail under Cache Components. Our data is fetched client-side behind auth, so server component caching adds nothing. Trade-off: revisit if upgrading to a Next.js major where the flag becomes mandatory. |
| 2026-10-09 | Test HTTP client | `httpx` vs. `httpx2` | **`httpx2`** | Starlette's `TestClient` deprecates `httpx` in favor of `httpx2`; dev/test-only dependency. |
| 2026-10-09 | Session mechanism | Server-side DB sessions vs. stateless JWT vs. JWT + sessions table | **Server-side sessions (`sessions` table)** | Sign out and expiry take effect immediately (delete/check the row). A JWT can't be revoked early without a denylist table, which is a sessions table again. Costs one primary-key lookup per request, which is negligible on SQLite. |
| 2026-10-09 | Session token storage | Raw token vs. SHA-256 hash in the DB | **SHA-256 hash as primary key** | A leaked `route53.db` yields no usable sessions. A fast hash is fine because the token is 256 random bits (nothing to brute-force), unlike a password. |
| 2026-10-09 | Session expiry | Fixed TTL vs. sliding expiry vs. cookie Max-Age only | **Fixed 12 h (`SESSION_TTL_HOURS`), checked server-side on every request** | Simple and predictable, about the same as the AWS console. Sliding expiry needs a DB write per request. Relying on Max-Age alone would let a copied token work forever. Expired rows are deleted on sight and swept at each login. |
| 2026-10-09 | Password hashing | `bcrypt` package vs. `pwdlib[argon2]` vs. `hashlib.scrypt` vs. passlib | **`bcrypt` directly** | Small, well known, salted and deliberately slow. passlib is unmaintained and breaks with bcrypt ≥ 4.1. bcrypt's 72-byte limit is enforced in the request schema (measured in UTF-8 bytes). All str↔bytes conversion lives in `security.py`. |
| 2026-10-09 | Token transport | httpOnly cookie vs. `Authorization: Bearer` header vs. cookie + CSRF token | **httpOnly cookie, `SameSite=Lax`, `Secure` via `COOKIE_SECURE`** | JS can't read it (XSS can't steal it); the browser sends it automatically through the same-origin proxy. `SameSite=Lax` plus JSON-only bodies blocks practical CSRF, so a separate CSRF token isn't needed. A bearer token would have to live in `localStorage`, and `proxy.ts` couldn't see it. |
| 2026-10-09 | User enumeration | Distinct vs. identical login errors | **Identical `401 "Invalid username or password"` + dummy bcrypt check for unknown users** | Neither the message nor the response time reveals which usernames exist. |
| 2026-10-09 | Session fixation | Keep vs. replace an existing session on login | **Replace** | Login deletes the session the browser already had and issues a fresh token, so a planted token can never become an authenticated session. |
| 2026-10-09 | Seeding the demo user | Alembic data migration vs. startup seed vs. `seed.py` script | **Alembic migration `0002`** | `alembic upgrade head`, already a setup step, yields a ready-to-use DB, and downgrade removes it. The migration calls `bcrypt` directly instead of importing app code, so it stays reproducible. Tests create their own users. |
| 2026-10-09 | Auth API shapes | Return the user vs. message bodies | **Login → `200 {id, username}`; logout → `204`, idempotent; me → `200`/`401`** | Login's body primes the frontend cache (no extra `/me` call). Logout never fails, so sign out always works even after the session has already expired. |
| 2026-10-09 | Validation error format | FastAPI default `422` (list) vs. global handler | **Global handler → `400 {"detail": "<field>: <message>"}`** | One error shape and the agreed status codes for every endpoint, now and later; the frontend's `ApiError` expects a string `detail`. |
| 2026-10-09 | Constraint naming | Unnamed vs. naming convention on `Base.metadata` | **Naming convention** | SQLite batch migrations can only drop or alter named constraints. Set before the first table existed, so there was nothing to rename. |
| 2026-10-09 | Frontend auth state | React Query `["me"]` query vs. React Context vs. Zustand | **React Query** | Already the chosen server-state library. The cache entry is the single source of truth; login, logout and any `401` update it, and components just read it. |
| 2026-10-09 | Route protection | `proxy.ts` + client guard vs. client guard only vs. `proxy.ts` calling `/me` | **`proxy.ts` (cookie present?) + `<AuthGuard>` (`/me`)** | Server redirect with no flash of protected UI, without adding a backend round-trip to every navigation. The guard catches expired or forged cookies. The backend `401` stays the real boundary. |
| 2026-10-09 | Redirect after sign-in / sign-out | — | **Expiry keeps `?next=`; explicit Sign out → plain `/login` (full page load)** | After an expiry the same user wants to continue where they were. After a deliberate sign-out the session is finished, and the next person shouldn't land on the previous user's page. A full reload also clears the old user's in-memory data and can't race the guard's redirect. `next` only accepts same-site paths (no open redirect). |
| 2026-10-09 | Sign-in page design | Replica of the AWS sign-in page vs. Cloudscape form branded as the clone | **Cloudscape form branded "Route 53 Clone", demo credentials shown, no sign-up** | AWS sign-in and sign-up belong to accounts/IAM, which are mocked and not part of Route 53. A replica of a real credential page hosted elsewhere is a phishing pattern. The real flow's fields (account ID, IAM user, MFA, payment verification) would be fake. See README. |
| 2026-10-09 | Hosted zone ownership (for Phase 3) | Global zones vs. zones scoped to a user | **`hosted_zones.user_id` FK; every zone/record query filtered by the signed-in user** | Matches how real resources belong to the account that created them, even with one demo user today. Another user's zone returns `404`. |
| 2026-10-09 | Create / edit hosted zone UI | Modals vs. full pages | **Full pages; delete is a modal where you type `delete`** | The real console uses full pages for create and edit, and a typed-confirmation dialog for delete. |
| 2026-10-09 | Hosted zones list actions | Per-row Actions column vs. row selection + header buttons | **Radio selection + header buttons** | Matches the console: View details / Edit / Delete act on the selected zone; the counter shows "(1/n)". |
| 2026-10-09 | Table search | Plain text filter vs. Cloudscape PropertyFilter | **PropertyFilter, "contains" (`:`) only** | Same tokens, property suggestions and "N matches" as the console. Filtering runs in the browser via collection-hooks. |
| 2026-10-09 | Zone name uniqueness | Allow duplicates (as AWS does) vs. `UNIQUE(user_id, name)` | **Unique per user, duplicate → `409`** | Deviation from AWS: a single-user demo gains nothing from duplicate names, and a duplicate is far more likely a mistake. |
| 2026-10-09 | Domain name validation | Library vs. own validator | **Own validator (`dns_names.py`)** | Small, well-defined rules (label length, letters/digits/hyphens, at least two labels), error texts in the console's wording, fully unit-tested. Names are stored lowercase with one trailing dot. |
| 2026-10-09 | Name servers | Random host names vs. Route 53's numbering | **Route 53's numbering** | `ns-N.awsdns-NN.<tld>`: N decides the top-level domain (512 per TLD) and the group number. One per TLD for public zones; the fixed set the console shows for private zones. |
| 2026-10-09 | Records table timing | Phase 4 vs. Phase 3 | **Phase 3** | Every zone needs its NS and SOA records from the moment it is created. Values are stored as a JSON list in `rdata`. |
| 2026-10-09 | Record count | Stored column vs. counted at query time | **Counted (join + GROUP BY in the list query)** | Can never drift from the real records; `records.zone_id` is indexed. |
| 2026-10-09 | Deleting a zone with records | Cascade-delete everything vs. refuse like Route 53 | **Refuse with `409` and Route 53's message while records other than NS/SOA exist** | Same behaviour as the console. The NS/SOA rows and VPC rows go via `ON DELETE CASCADE`. The dialog warns when the zone has more than its 2 default records. |
| 2026-10-09 | Private zone VPCs | JSON column vs. child table | **`hosted_zone_vpcs` table, `UNIQUE(zone_id, vpc_id)`** | Queryable, constrained and cascades with the zone. |
| 2026-10-09 | VPC data | Free-text VPC IDs vs. mocked catalog | **Mocked catalog (`mock_vpcs.py`, `GET /api/vpcs`)** | 35 Regions as in the console's dropdown, one stable fake VPC each; unknown VPCs give the console's "The VPC ID is invalid." |
| 2026-10-09 | Editing a zone | Description only vs. description + VPCs | **`PATCH` changes the description and, for private zones, replaces the VPC list** | The console's edit page allows both. Rows that stay are kept (not deleted and re-inserted), which would break the unique constraint. |
| 2026-10-09 | Tags | Implement vs. show only | **Shown, not functional** | The console's empty states are rendered; real tags would need a new table and API for a feature outside the core scope. |
| 2026-10-09 | Notifications | Toast library vs. Cloudscape Flashbar | **Flashbar with stacked items, kept across navigation** | The console's own component. Every API error uses one format: "Error occurred / Please try again later. / (<detail>)". |
| 2026-10-09 | Backend layering | Logic in routers vs. service layer | **`services/zones.py`; routers only map HTTP** | Zone rules (IDs, name servers, delete check) are testable on their own and the routers stay thin. |
| 2026-10-09 | Split panel | Fixed vs. per page | **Per-page default width (412 list / 643 details), resizable, closed by default on narrow screens** | Matches the console's widths; on a phone it would cover the table. |
| 2026-10-09 | Records table filters | Separate dropdown filters vs. dropdowns that add tokens | **Dropdowns add "Property = value" tokens** | How the console behaves; one source of truth for all filters. Layout switches by the filter's own width (container queries), because the split panel also takes space. |
| 2026-10-09 | Primary button colour | Cloudscape default blue vs. console orange | **Cloudscape theming: #ff9900, hover #fa6f00** | Values taken from the console's stylesheet. |
| 2026-10-09 | Side navigation | Five links vs. the console's full structure | **Full structure; unbuilt pages show "Coming soon"** | Looks like the real console; unknown URLs are still a 404. |
| 2026-10-09 | Bulk record changes (Phase 4) | Single-record endpoints looped by the frontend vs. list-taking create + `batch-delete` vs. one Route 53-style `changes` endpoint | **`POST /records` takes a list; `DELETE /records/{rid}` plus `POST /records/batch-delete {ids}`; all or nothing** | The console's "Create records" and "Delete N selected records?" act on several records, and Route 53 applies a change batch atomically. A frontend loop could leave half the records created. Keeps the REST shape of the other endpoints and covers the "Bulk operations" bonus. |
| 2026-10-09 | Record value validation | `dnspython` vs. own module | **Own `record_values.py` (standard library `ipaddress` for addresses)** | Same reasoning as zone names: small, fully tested, and errors in Route 53's wording (`… encountered with '<value>'`, as the console's banner prints it) using the console's own format hints. `dnspython` would add a dependency whose messages don't sound like the console. |
| 2026-10-09 | Record uniqueness | Service checks only vs. DB constraint + service checks | **Migration `0004`: `UNIQUE(zone_id, name, type)`; the service checks first for Route 53's `409` message** | Same pattern as zones: a friendly message, with the database as the backstop against two racing requests. CNAME exclusivity and the protected SOA/apex NS can't be constraints, so they live in `services/records.py`. |
| 2026-10-09 | Record name in the API | Relative ("www") vs. fully qualified | **Fully qualified, like the Route 53 API** | One unambiguous form in requests, responses and the database; the console's form adds the zone name to the subdomain box itself. Names outside the zone get Route 53's "not permitted in zone" error. |
| 2026-10-09 | Error status for Route 53 rule violations | Always `400` (Route 53's `InvalidChangeBatch`) vs. `400`/`409` by kind | **`409` when the request clashes with existing records (duplicate, CNAME conflict); `400` when it can never be valid (bad value, CNAME at apex, deleting SOA/apex NS)** | Keeps the project's convention (`409` = conflict with existing data) while using Route 53's message texts. |
| 2026-10-09 | Unimplemented record features | Model routing policies/alias now vs. later | **Simple routing, non-alias only** | The PDF asks for the record types, not routing policies; the table already shows "Simple" / "No". The schema notes how a `set_identifier` would extend the unique constraint. |
| 2026-10-09 | Errors the console words specially | Frontend matches the message text vs. an error `code` | **Optional `code` next to `detail` (`errors.py`), only where needed: `RecordSetAlreadyExists`** | The console's banner says "A record with the specified name already exists." for that error and "Please try again later." for the rest. A code is robust where matching text isn't; every other error keeps the plain `{"detail"}` shape. |
| 2026-10-09 | Record order | Creation order vs. Route 53's | **DNS order: labels read from the right, then type** | The console lists `test345`, `test456`, `test55` by name whatever their creation order, apex NS/SOA first. Sorted in Python (`dns_names.dns_order`): SQL can't order by reversed labels, and a zone's records are already loaded. |
| 2026-10-09 | Editing a record's name/type | Fixed vs. editable | **Editable, except SOA and apex NS** | The console's edit panel has editable Record name and Record type fields (read-only only for the apex NS/SOA). Route 53 treats it as delete + create, so the new name + type goes through the create checks. |
| 2026-10-09 | "View status" (record changes) | Changes table vs. frontend-only page vs. disabled button | **`changes` table (migration `0005`), `GET /api/changes/{id}`, Change Info page** | The console's create/edit banners open a Change Info page (ID, submitted time, PENDING → INSYNC). A table survives a reload and works from any device; the frontend-only version would forget the change on refresh. |
| 2026-10-09 | Change status | Stored + background job vs. computed | **Computed from `submitted_at`: PENDING for 30 s, then INSYNC** | Mimics Route 53's propagation ("within 60 seconds") without a scheduler; can never get stuck. |
| 2026-10-09 | Returning the change from mutations | Response header vs. envelope | **Envelope: `POST` → `{records, change_info}`, `PATCH` → `{record, change_info}`** | Visible in the OpenAPI docs and typed on both sides; `change_info` is Route 53's own name. Delete stays `204` and records no change, since the console's delete banner has no "View status". |
| 2026-10-09 | Unimplemented options on the record form | Hide vs. show disabled | **Show disabled: the 7 other record types, 7 other routing policies, Alias, "Switch to wizard"** | The dropdowns then list exactly what the console's do (screenshot Record_Types), and nothing pretends to work. |
| 2026-10-09 | Record form validation | Client-side rules vs. server-side | **Only the console's own client check ("Record name is required for NS records.") and its leading/trailing-space warnings; everything else comes back from the API in the error banner** | That's how the console behaves (Error_Invalid_value): Route 53 validates values on the server. One set of rules, in `record_values.py`, tested once. |
| 2026-10-09 | Edit record UI | Separate page vs. modal vs. split panel | **Split panel, replacing Record details ("Edit record")** | Where the console edits (screenshots 07, Edit_Record_ErrorLocation). The panel is keyed by the selection, so selecting another record leaves the form; a save clears the selection, as in the console. |
| 2026-10-09 | One form for create and edit | Two forms vs. shared `RecordFields` | **Shared, with `ColumnLayout` instead of `Grid`** | Same fields, texts and rules in both places. `ColumnLayout` sizes by its container (two columns on the page, one in the narrow panel); `Grid` sizes by the window and would squeeze the panel. |
| 2026-10-09 | Deleting records UI | Typed confirmation (like zones) vs. the console's list dialog | **The console's dialog: the selected records in a searchable table, Cancel / Delete, no typed word** | Screenshots 10 and Delete_REcord_1. One `batch-delete` call, so several records go all or none. The success banner keeps the console's plural wording even for one record (Delete_Record_2). |
| 2026-10-09 | Refresh after a failed delete | Only after success vs. after any outcome | **After any outcome (`onSettled`)** | A failure such as `404` means the records changed elsewhere; refetching keeps the table from showing a record that's gone. |
| 2026-10-09 | Top bar branding | AWS smile logo vs. text "Route 53 Clone" vs. neutral icon + text | **Text "Route 53 Clone"** | Same reasoning as the sign-in page: no AWS trademark on a page that isn't AWS. Everything else in the bar follows the console. The footer's copyright line names the clone, not AWS. |
| 2026-10-09 | Top bar structure | Cloudscape `TopNavigation` structured props vs. custom content (`children`) | **Custom content with the `top-navigation` visual context** | Matches the console's layout: search next to Services, the two-line account label hanging from the account-colour strip, popovers on unavailable controls. The structured mode can't show popovers and centres the search. Trade-off: narrow screens are handled with our own media query (≤ 688px keeps identity, Help, Settings, account). |
| 2026-10-09 | Top bar search | Decorative vs. pages + hosted zones vs. full search (zones and records) | **Pages + hosted zones (Autosuggest), Alt+S focuses it** | Useful without a new endpoint: it reuses the side-navigation data and the cached zone list, fetched only once the box is used. Searching records would need a backend search API. |
| 2026-10-09 | Controls the clone doesn't have | Disabled vs. "Coming soon" popover vs. hidden | **Shown; clicking opens a "not available in this Route 53 clone yet" popover** | Same idea as the "Coming soon" pages: the bar looks like the console and nothing pretends to work. "Global" shows the console's own text, "Route 53 does not require region selection." Help & support links to the public AWS pages (re:Post, documentation, training); Support Center and feedback are disabled. |
| 2026-10-09 | Mock account ID | Derived in the frontend vs. `users.account_id` column vs. constant | **Derived from the user id (`lib/account.ts`, FNV-1a)** | Accounts are out of scope, so a cosmetic value doesn't justify a migration. Stable per user on every device; account name = username. |
| 2026-10-09 | Font | Amazon Ember (the console's) vs. Open Sans (Cloudscape's) | **Open Sans** | Amazon Ember isn't freely licensed. Known visual difference from the console. |
| 2026-10-09 | Account menu | Cloudscape Popover vs. own panel | **Own panel inside the top bar (`AccountMenu`)** | Screenshot AccountDropdown: the console's menu is a dark panel attached under the bar at the window edge, with no header or close button, and the tab's caret flips. A Popover is light, has a header, and points at its trigger. The panel closes on an outside click or Escape (focus returns to the tab); clicks in its "not available" popovers count as inside. |
| 2026-10-09 | Primary buttons in the top bar | Accept Cloudscape's blue vs. theme the `top-navigation` context | **Theme the context (orange)** | The console's Sign out is orange. Cloudscape's theme generator drops a context value that is the same string as the global one, so the context's colours are written in uppercase (`ConsoleTheme.tsx`). |
